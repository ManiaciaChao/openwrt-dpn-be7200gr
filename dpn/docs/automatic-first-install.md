# 设备内自动首次安装（automatic-v1）

这是新的待实机验收实现。它不连接实验路由器、不改写已发布 RC2，也不把新的镜像
视为已经通过 RC2 的验收。默认 factory 打包模式改为 `automatic`；
`--first-install host` 可构建旧的主机辅助 RAM 模式。

## 执行过程

原厂仍只上传 UMMtk 容器里的 `tclinux` 载荷，不包含 `tcboot`。
原厂重启进入的仍是 RAM 环境，但用户无需操作这个环境。

1. factory 根文件系统中的 `automatic-v1` 标记和设备树中的
   `factory-auto-install` 必须同时存在，procd 才能启动唯一的自动安装事务。
   普通 OpenWrt、独立恢复和旧的 host 模式不会自动格式化。
2. 检查原厂启动槽、三个内置载荷的 SHA256、FIP/根文件系统绑定和无持久挂载状态。
   由现有内核资格门检查 NAND/BMT 后再继续，不扩大可写物理范围。
3. 现场生成 SSH 主机密钥和恢复客户端密钥。恢复公钥放入授权文件，客户端私钥保留在
   新配置 `/etc/dpn-recovery/` 中，随配置备份、标准升级及物理恢复默认设置保留。
4. 新原生 `dpn-vault-build` 只读物理 NAND，生成原有 VLT4 格式的每机资料。
   它保存必要 vendor 状态、校准指纹、原厂完整槽/vendor 摘要和恢复身份；不导出
   完整原厂槽/vendor 备份。必要状态 gzip 会在 RAM 内实际解压逐字节比对。
5. 调用原有 REC16/VLT4 header-last 写入器，全回读 20 MiB，核对保护区，选择恢复槽。
6. 不重启、不等浏览器/SSH 接力，直接调用现有标准 RAM 升级后端 `dpn_l4_install`：
   建立 UBI、写入并回读根文件系统、恢复并比对初始配置、header-last 写主内核，
   最后切换正常槽并重启。

**与 RC2 的差异：** 自动流程在数据迁移前验证恢复镜像及 vault 的完整 NAND 回读，
但不先重启到独立恢复再迁移。RC2 的这个额外实机启动检查点需要外部主机保存并
重新上传载荷，不能直接沿用到无主机流程。新流程复用标准 sysupgrade 的 RAM 写入
路径；必须另外验证首次安装成功后的独立恢复启动。

## 备份和故障语义

完整原厂备份是用户刷机前的可选独立操作，不是安装状态机的前提，也不会在安装后
凭空提供。若没有完整原厂槽/vendor 备份，不保证完整回原厂。恢复访问密钥是每机生成的，
应在安装成功后从配置备份中导出；若首次安装在密钥尚未可导出时失败，不能承诺用户
已具备独立恢复的 SSH 访问能力。

状态和私有日志位于 RAM 的 `/tmp/dpn-factory-auto.status`、
`/tmp/dpn-factory-auto.log`。事务目录排他创建，procd 不设置 respawn，任一步失败都停止，
不自动重试擦写或重启。既有 vault 会拒绝自动重新安装；这不是任意中断状态下的自动续装器。
上述记录会在重启后丢失，不能把 RAM 事务锁称为掉电恢复日志。

## 离线检查和实机测试

离线测试包括：原生 vault 对照独立 Python 深度解析，两种原厂槽、无源数据变更、
输出排他、错误校准/既有 vault/容量不足拒绝；真实 shell 协调器的各阶段失败和
重复启动拒绝；初始配置归档、每机独立密钥以及标准备份/重置保留。
构建时检查实际镜像内容、原厂 50 MiB 槽容量，以及 factory/sysupgrade 正常载荷一致。

待用户回来后验证：原厂 Web 上传一次、无外部命令的自动安装、正常 Flash 启动、
默认地址/DHCP/LuCI 设置密码、配置备份中恢复访问密钥、实际独立恢复启动、
匹配 sysupgrade 及最终物理冷启动。首次自动安装与全部故障恢复场景仍未取得实机资格。
